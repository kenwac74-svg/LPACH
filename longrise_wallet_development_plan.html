Developer Planning Document

LONGRISE 입출금 및 SEND 개발 기획서

본 문서는 실제 백엔드/프론트엔드 개발을 위한 구현 기준이다. 1인 개발 체제를 고려하여 1단계는 TRC20 USDT 입출금 테스트, 내부 Ledger 분리, 최소 집금 정책을 우선한다.

1. 단계별 개발 범위

단계회원 수목표개발 범위
1단계100명 미만최소 입출금 테스트TRC20 입금 감지, 19 컨펌, Ledger 반영, 최소 집금 정책, SEND, 출금 요청, 관리자 확인, UTC 09:00 배치 처리
2단계100명 이상리스크 통제 강화Buffer/Vault/Payout 역할 분리, 한국 거래소 직접 입출금 자동 차단, Basic On-chain Risk Screening, 출금 수수료 현실화 검토
3단계1000명 이상운영 자동화Energy 임대 연동, 지갑 유동성 알림, 고액 출금 승인 룰 고도화
3단계 이후1000명 이상 안정 운영 후체인 확장TRC20 외 테더 사용량 상위 3개 체인을 선정하여 순차 지원

3. 개발자 의사결정 참고표

아래 항목은 개발자가 구현 난이도와 운영 리스크를 함께 보고 최종 구현 순서를 판단하기 위한 비교표다. 현재 확정 정책은 1단계 최소 구현을 우선한다.

항목선택지장점단점현재 결정
3-Tier 지갑 격리 1단계 즉시 적용 vs 2단계 적용 즉시 적용 시 CEX 동결/오염 자금 전염 방어가 강함 1인 개발 체제에서 Buffer/Vault/Payout 전체 자동화까지 구현하면 지갑 운용, 예외 처리, 집금 로직 부담이 큼 완전한 3-Tier는 2단계 적용. 단, 1단계부터 Stage-1 Collection Wallet 집금 정책은 적용
최소 출금액 10 USDT vs 50 USDT 10 USDT는 Flexible 상품 유저가 현실적으로 출금 가능. 50 USDT는 운영 부담 감소 10 USDT는 소액 출금 증가. 50 USDT는 소액 유저에게 사실상 출금 제한처럼 느껴질 수 있음 10 USDT 확정
출금 수수료 1 USDT vs 2.5 USDT 1 USDT는 초기 유저 친화적. 2.5 USDT는 회사 비용 방어에 유리 1 USDT는 회사가 네트워크 비용 일부를 부담할 수 있음. 2.5 USDT는 10 USDT 출금 기준 체감 수수료가 큼 1단계 1 USDT, 2단계부터 현실화 검토
Energy 임대 1단계 필수 vs 3단계 최적화 필수 적용 시 출금 비용 최적화 가능 API 장애, 임대 실패, 비용 산정, 예외 처리가 늘어남 3단계 검토
4중 AML / Risk Screening 1단계 적용 vs 2단계 적용 초기부터 자동 차단 가능 무료 API 한계, 장애 대응, 오탐/미탐 처리 부담 2단계 적용
출금 주소 방식 매번 임의 입력 vs 메인/서브 사전 등록 사전 등록 방식은 블랙리스트 관리, 계정 탈취 대응, 오입력 방지에 유리 유저가 주소 변경 시 OTP와 관리자 승인을 기다려야 함 메인 1개 + 서브 1개 유지

6. SEND 개발 스펙

항목구현 기준
정의플랫폼 내부 유저 간 USDT 장부 이전. 온체인 트랜잭션이 아니다.
수취자 식별유저명 또는 플랫폼 고유번호로 검색. 최종 확인 팝업에는 수취자 표시명을 반드시 보여준다.
차감 재원Withdrawal Balance 안의 출금 가능 USDT만 사용한다.
차단 재원bonus_usdt, package_value, pending_withdrawal, locked_review, CNYT는 SEND 불가.
수수료1단계 무료 권장. 네트워크 수수료 없음.
처리 방식DB transaction 안에서 sender debit과 receiver credit을 동시에 기록한다.
실패 처리수취자 없음, 잔액 부족, 제한 계정, 자기 자신에게 전송 시도, DB 처리 실패를 별도 에러 코드로 반환.
완료 후취소 불가. Transfer History에 내부 Ledger ID와 상세 로그 표시.
 
POST /api/wallet/send
Request:
{
  "receiverUserCode": "LR-10293",
  "amount": "25.00"
}

Validation:
- sender account active
- receiver exists and active
- amount > 0
- available withdrawal balance >= amount
- source balance types are sendable

Success:
{
  "status": "COMPLETED",
  "sendTransferId": "send_...",
  "ledgerDebitId": "ledger_...",
  "ledgerCreditId": "ledger_..."
}

7. 출금 주소 관리 개발 스펙

항목구현 기준
주소 슬롯유저당 체인별 MAIN 1개, SUB 1개만 허용한다.
출금 요청유저는 승인 완료된 출금 주소 중 하나를 선택해서 출금한다. 임의 주소 직접 입력은 제공하지 않는다.
주소 등록TRON 주소 형식 검증, 한국 거래소 직접 주소 블랙리스트 검사, OTP 인증, 관리자 승인 후 APPROVED 처리.
주소 변경기존 주소를 바로 덮어쓰지 않고 변경 요청 레코드를 생성한다. 승인 전까지 기존 승인 주소만 출금 가능.
관리자 승인주소, 체인, 유저 이메일, 고유번호, 요청 시간, 블랙리스트 검사 결과를 보고 승인/거절한다.
보안 효과주소 바꿔치기, 탈취 계정 출금, 한국 거래소 직접 출금, 반복 주소 검사 부담을 줄인다.

9. 집금 정책 개발 스펙

10. Payout Reserve 개발 스펙

Payout Reserve는 유저 화면에 노출하는 기능이 아니라 관리자 운영 기능이다. 목적은 상품 구매로 확정된 자금 규모 대비 회사가 출금, 매일 수익 지급, 중도 해지 대응에 사용할 별도 유동성을 충분히 보유하고 있는지 확인하는 것이다.

항목구현 기준
필요 Reserve 계산required_reserve_amount = total_confirmed_package_purchases * 0.35
현재 유동성 계산Payout Wallet 및 별도 Payout Reserve Wallet의 사용 가능 USDT 합계
Reserve 비율reserve_ratio = current_payout_liquidity / required_reserve_amount
정기 점검일매월 10일과 25일에 snapshot 생성 및 부족분 계산
주의 경보Reserve 비율이 90% 미만이면 관리자 대시보드에 WARNING 표시
긴급 경보Reserve 비율이 80% 미만이면 CRITICAL 표시 및 회사 자금 보충 필요 알림
운영 단순화1~2단계에서는 상품별 Reserve 비율을 두지 않고 전체 확정 구매금액 기준으로만 관리
자금 이동 제한Collection/Vault 계열 자금을 Payout Wallet로 직접 이동시키는 로직은 만들지 않는다.
관리자 대시보드에는 Total Confirmed Package Purchases, Required Payout Reserve, Current Payout Liquidity, Reserve Gap, Reserve Status, Last Funding Date, Next Review Date를 표시하는 것을 권장한다.

11. 프론트엔드 필수 표시

  • Deposit: TRC20 USDT 주소, 컨펌 상태, 최소 입금 인정액.
  • Withdraw: 승인된 메인/서브 출금 주소 선택, 최소 출금 10 USDT, 수수료 1 USDT, 예상 수령액, UTC 09:00 처리 안내.
  • Fee Notice: 1단계 수수료는 1 USDT이나 TRON 네트워크 상황에 따라 향후 1~2 USDT 범위에서 변경될 수 있음을 표시.
  • Withdrawal Address: 메인 1개/서브 1개, OTP 인증, 관리자 승인 대기/승인/거절 상태 표시.
  • SEND: 수취 유저명/고유번호, 금액, 취소 불가 확인 팝업, 성공/잔액부족/실패 결과 팝업.
  • History: Deposit, Withdraw, SEND, Receive, Reward, Package를 구분 표시.
